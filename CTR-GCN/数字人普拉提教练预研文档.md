# 数字人普拉提教练接入预研文档

## 1. 背景与目标

当前项目主线已经具备“摄像头采集骨架 → 数据集 → 动作识别模型训练”的基础能力，但如果要升级为“数字人普拉提教练”，系统目标会从单纯的动作分类，提升为“实时姿态理解 + 动作标准度判断 + 教练式反馈”。

本预研文档的目标是回答三个问题：

1. 现有 CTR-GCN / MediaPipe 方案是否足以支撑普拉提数字教练？
2. 是否需要引入新的姿态估计模块（例如 `rtmlib` / RTMPose）？
3. 项目应如何分阶段接入，才能用最少成本验证效果？

---

## 2. 业务目标拆解

普拉提数字教练不是一个单一的动作识别问题，而是一个多阶段链路：

```text
摄像头视频
  -> 人体姿态估计
  -> 关键点平滑与归一化
  -> 动作阶段识别
  -> 动作质量评估
  -> 错误类型判断
  -> 数字人话术反馈
```

对应的能力可拆成以下四层：

### 2.1 姿态估计
负责从视频中提取人体关键点，输出稳定的骨架序列。

### 2.2 动作识别
识别用户当前在做什么动作，例如臀桥、卷腹、平板支撑等。

### 2.3 动作标准度判断
判断动作是否标准，常见错误包括：

- 膝盖内扣
- 骨盆抬不够
- 腰椎塌陷
- 肩膀耸起
- 动作幅度不足
- 节奏过快或过慢

### 2.4 数字人反馈
将识别结果转成自然语言提示，让数字人输出：

- 动作鼓励
- 错误提醒
- 调整建议
- 节奏提醒

---

## 3. 现有项目能力评估

当前仓库的主线更偏向“骨架动作识别训练项目”，核心路径是：

```text
摄像头采集
  -> MediaPipe 提取 pose / hands 骨架
  -> 保存为数据集
  -> 训练动作识别模型
  -> 评估结果
  -> 导出/部署
```

从预研角度看，现有项目已经具备以下基础：

- 骨架数据采集流程
- 基于骨架序列的模型训练能力
- CTR-GCN / TCN 等动作识别模型基础
- 训练评估与导出路径

但对于普拉提数字教练，还缺少以下关键部分：

- 更适合居家/运动场景的姿态估计输入
- 面向普拉提的动作标签体系
- 动作错误样本与质量标签
- 实时反馈链路
- 数字人输出接口

---

## 4. MediaPipe 是否足够

### 4.1 优点

MediaPipe 的优点是：

- 上手快
- 工程成熟
- 适合实时推理
- 浏览器端或轻量端部署方便

### 4.2 局限

在普拉提场景中，MediaPipe 常见问题包括：

- 仰卧、侧卧姿态不稳
- 手脚遮挡时关键点抖动较大
- 相机视角变化导致深度估计不稳定
- 局部动作幅度较小时，关键点误差对角度影响大

### 4.3 结论

MediaPipe 可以作为基线方案，但不建议作为最终方案直接定型。对于“动作标准度评估”场景，姿态质量越高，后续规则与模型的效果越稳定。

---

## 5. 是否考虑接入 `rtmlib`

`rtmlib` 可以作为姿态估计层的替代或增强方案，适合作为预研对象。

### 5.1 适合接入的原因

- 可能比 MediaPipe 更适合复杂姿态
- 对人体关键点质量有机会提升
- 更适合做“关键点 -> 角度 -> 规则判断”的链路
- 便于后续和自训模型对接

### 5.2 接入定位

`rtmlib` 更适合作为“关键点提取器”，而不是完整动作识别方案。推荐把它放在链路前端：

```text
摄像头
  -> rtmlib / RTMPose
  -> 关键点归一化
  -> 关节角度与时序特征
  -> 动作阶段识别
  -> 标准度判断
  -> 数字人反馈
```

### 5.3 预研判断

如果在真实普拉提摄像头场景中，`rtmlib` 的关键点比 MediaPipe 更稳，那么它值得进入主线；否则仍然可以保留 MediaPipe 作为轻量方案。

---

## 6. 推荐的系统架构

### 6.1 第一版推荐架构

```text
摄像头
  -> 姿态估计（MediaPipe 或 rtmlib）
  -> 关键点滤波 / 平滑
  -> 归一化与特征工程
  -> 动作阶段识别
  -> 规则 + 轻量模型评估
  -> 教练提示生成
  -> 数字人播报
```

### 6.2 为什么不建议直接上纯 GCN

纯 GCN 直接做动作分类的问题是：

- 对数据量敏感
- 对摄像头角度敏感
- 对姿态质量敏感
- 很难解释“错在哪里”

而普拉提教练最需要的其实是“可解释纠错”，不是单纯的类别输出。

---

## 7. 推荐的技术路线

### 阶段一：姿态估计替换验证

目标是比较 MediaPipe 与 `rtmlib` 的关键点稳定性。

验证指标：

- 关键点丢失率
- 关节角波动
- 仰卧/侧身姿态稳定性
- 实时帧率
- 延迟

输出：

- 基线方案是否继续用 MediaPipe
- 是否切到 `rtmlib`

### 阶段二：小动作集原型

不做大而全动作识别，先选 5～8 个高频普拉提动作。

推荐动作示例：

- 臀桥
- 平板支撑
- 卷腹
- 鸟狗式
- 蚌式开合

每个动作先采集：

- 正确样本
- 常见错误样本
- 不同角度样本

### 阶段三：规则优先的标准度评估

先用规则系统输出可解释判断，例如：

- 膝盖是否内扣
- 骨盆是否抬高到位
- 躯干是否稳定
- 动作保持时间是否足够

### 阶段四：轻量时序模型增强

在规则基础上，再引入：

- TCN
- BiLSTM
- 轻量 Transformer

用于处理动作阶段和时间连续性。

### 阶段五：数字人话术接入

把结果转成提示词，由数字人输出：

- 简短鼓励
- 标准提示
- 错误纠正
- 节奏提醒

---

## 8. 数据集预研建议

### 8.1 最小可用数据规模

如果目标是先做原型验证：

- 每个动作 20～30 段正确样本
- 每个动作 20～30 段错误样本
- 5～8 个动作即可开始验证

### 8.2 更稳妥的数据规模

如果目标是形成可用版本：

- 每个动作 50～100 段正确样本
- 每个动作 50～100 段错误样本
- 覆盖不同角度、身材和光照

### 8.3 标注建议

建议标注至少包含：

- 动作类别
- 动作阶段
- 是否标准
- 错误类型
- 错误严重程度

---

## 9. 工程落地建议

### 9.1 当前仓库最适合的接入方式

建议保留现有训练主线，把数字人普拉提教练作为一个独立实验分支或子模块，不要和原有动作识别训练流程强耦合。

### 9.2 推荐的模块边界

```text
采集层
  -> 姿态估计层
  -> 特征层
  -> 动作识别/质量评估层
  -> 提示生成层
  -> 数字人展示层
```

### 9.3 部署建议

如果前端是 Electron 或 Web 客户端，推荐：

- 前端负责视频采集与展示
- 本地 Python 服务负责姿态与模型推理
- 通过 WebSocket / HTTP 传输关键点或推理结果

不要一开始就把整段视频上传到后端，优先传关键点序列或摘要结果。

---

## 10. 风险与挑战

### 10.1 数据域差异

瑜伽数据集不等于普拉提数据集。直接迁移训练模型大概率存在明显性能偏差。

### 10.2 视角问题

普拉提动作中仰卧、侧卧、局部遮挡会明显影响关键点质量。

### 10.3 质量判断难

标准度判断比动作分类更难，因为需要结合几何规则、时序和动作阶段。

### 10.4 数字人反馈稳定性

如果反馈频率过高或误报过多，会严重影响用户体验。

---

## 11. 结论与建议

### 11.1 结论

这个项目可以接入数字人普拉提教练方向，但建议不要直接沿用“MediaPipe + GCN 单模型分类”的思路，而应将问题拆解为：

1. 更稳的姿态估计
2. 小规模普拉提动作集
3. 规则优先的质量评估
4. 轻量时序模型增强
5. 数字人反馈接口

### 11.2 推荐决策

- `rtmlib` 值得作为姿态估计候选方案进行预研
- MediaPipe 可作为基线保留
- 动作识别不要一开始追求大类别数
- 先做可解释的纠错，再做更复杂分类

### 11.3 推荐下一步

1. 采集真实普拉提视频做姿态质量对比；
2. 以 5 个动作做小数据集原型；
3. 验证 `rtmlib` 与 MediaPipe 的差异；
4. 先实现规则纠错版数字人提示；
5. 再决定是否引入更复杂的 GCN / 时序模型。
